# AIRE Trace Schema

This document specifies the JSON representation of a trace, the validation rules enforced at write time, and the layout of a stored run. The authoritative definitions are in `src/aire/schema.py` (dataclasses and `validate_trace_dict`) and `src/aire/tracing/storage.py` (`RunStore`).

## Overview

A trace is the complete, serialisable record of one system invocation for one evaluation case. Everything downstream (metrics, judges, failure classification, regression, reports) reads traces; nothing re-runs the system. All fields are JSON-serialisable, every trace is validated before it is stored, and stored traces are never rewritten.

## Field reference

### Trace (top level)

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `run_id` | string | yes | Id of the run this invocation belongs to (format `run_<8 hex>`) |
| `case_id` | string | yes | Id of the evaluation case, joins the trace to its `EvalCase`; unique within a run |
| `trace_id` | string | yes | Unique trace id (format `tr_<8 hex>`, generated by `new_id("tr")` when not supplied) |
| `system_config` | object | no | Fingerprint of the system version and config (for the demo: `top_k`, `min_score`, `style`, `weighting`, `allow_irrelevant`) |
| `started_at` | float | no | Invocation start, unix seconds |
| `final_answer` | string or null | no | The answer the system returned; null or empty means no answer was produced, which the engine scores as a failed invocation |
| `retrieved_doc_ids` | list of string | no | Document ids returned by retrieval, in rank order |
| `tool_calls` | list of object | no | Recorded tool calls; each is an object with a string `name`, plus `args` and a `valid` flag from schema validation |
| `spans` | list of Span | no | Ordered, timed steps of the invocation; the runner writes one root span per attempt, and the async runner adds the system's own steps (retrieval, one span per model attempt) as children of that root |
| `usage` | Usage | no | Token accounting |
| `error` | string or null | no | Non-null means the whole invocation failed (exception, timeout or an error reported by the system) |
| `schema_version` | string | written | Trace schema version, currently `"1.2"`; added on serialisation (1.2 added span ids and token breakdowns) |

### Span

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `kind` | string | yes | One of `retrieval`, `generation`, `tool_call`, `custom` |
| `name` | string | no | Human-readable step name, for example `v1_baseline.invoke` or `qdrant.search` |
| `started_at` | float | no | Span start, unix seconds |
| `latency_ms` | float | yes | Duration in milliseconds, must not be negative. For runner spans it excludes client-side pacing (`SystemUnderTest.before_invoke`) and any wait the system reports in `SUTResult.wait_ms` |
| `attributes` | object | no | Free-form annotations. The runner writes `attempt` and, when the system reports them, `wait_ms` and its own fields (the LLM responder adds `provider_attempts`, `model`, `finish_reason`, or `http_status` on failure) |
| `error` | string or null | no | Non-null means this span failed. A timed-out or raising attempt gets a span with its error; `TraceRecorder` span timers set it automatically |
| `span_id` | string | no | Written only when set (format `sp_<8 hex>`). The async runner gives every root span an id |
| `parent_id` | string | no | Written only when set: the id of the root span this step belongs to. Latency in the engine sums root spans only, so child spans are never counted twice. A root span with `attributes.cache_hit: true` was answered from the response cache and has no latency in the results |

### Usage

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `prompt_tokens` | int | no | Prompt token count, must not be negative |
| `completion_tokens` | int | no | Completion token count, must not be negative |
| `token_source` | string | no | Provenance label: `api` (reported by a real backend), `heuristic` (estimated at about 4 characters per token by `estimate_tokens`), `none` (unknown, for example a failed call; tokens are 0), or `unknown` (the dataclass default). Heuristic counters are allowed but must be labelled; failed calls are never filled with an estimate. |

| `cache_read_tokens` | int or null | no | Prompt tokens served from the provider's prompt cache, as the provider reported them; already part of `prompt_tokens` |
| `cache_write_tokens` | int or null | no | Prompt tokens written to the provider's prompt cache (Anthropic); already part of `prompt_tokens` |
| `reasoning_tokens` | int or null | no | Thinking or reasoning tokens; already part of `completion_tokens` |

`total_tokens` is a derived property (`prompt_tokens + completion_tokens`) and is not stored. The breakdowns are null when the provider did not report them and are never added to the total again.

## Annotated example

A real trace from the committed v1 baseline run (`results/v1_baseline/traces.jsonl`, case `refunds_request_window`), annotated:

```jsonc
{
  "run_id": "run_f3e318af",              // joins all traces of one experiment
  "case_id": "refunds_request_window",   // joins to the EvalCase in the dataset
  "system_config": {                     // SUT fingerprint, identical for the
    "top_k": 1,                          // whole run; the regression engine and
    "min_score": 0.05,                   // reports use it to label versions
    "style": "faithful",
    "weighting": "overlap",
    "allow_irrelevant": false
  },
  "started_at": 1795103198.1158,       // unix seconds
  "final_answer": "Northwind Cloud grants a refund window of 30 days from the date of each charge. [doc:doc_refunds] To request a refund, ... [doc:doc_refunds]",
  "retrieved_doc_ids": ["doc_refunds"],  // rank order; read by recall@k and MRR@k
  "tool_calls": [],                      // empty: this system makes no tool calls
  "spans": [
    {
      "kind": "generation",              // one span per attempt; a multi-step SUT
      "name": "v1_baseline.invoke",      // would add retrieval and tool_call spans
      "started_at": 1795103198.1158404,
      "latency_ms": 1.245299999936833,  // measured with Timer (perf_counter)
      "attributes": {"attempt": 1},      // retry bookkeeping by the runner
      "error": null
    }
  ],
  "usage": {
    "prompt_tokens": 13,                 // heuristic estimate (~4 chars/token)
    "completion_tokens": 52,
    "token_source": "heuristic",         // provenance label, not a real API count
    "cache_read_tokens": null,           // breakdowns: null when not reported
    "cache_write_tokens": null,
    "reasoning_tokens": null
  },
  "error": null,                         // non-null would classify as invocation_error
  "trace_id": "tr_4966e8b6",
  "schema_version": "1.2"
}
```

The corresponding `eval_results.json` row shows how the trace is scored against its case (`expected_keywords: ["30 days", "full refund", "payment card"]`, `supporting_doc_ids: ["doc_refunds"]`): `keyword_recall: 0.3333`, `gold_citation_recall: 1.0`, `citation_precision: 1.0`, `groundedness: 1.0` (both quoted sentences are cited and verbatim), `retrieval_recall_at_1: 1.0`, `retrieval_recall_at_3: 1.0`, `retrieval_mrr_at_3: 1.0`, `errors: 0`, `failure: "incomplete_answer"` (only one of the three keywords is in the answer).

## Validation rules

`validate_trace_dict(d)` returns a list of problems; an empty list means valid. Rules:

1. `run_id`, `case_id`, and `trace_id` must be present and non-empty.
2. Every span must have a `kind` field (reported as `span[i]: missing 'kind'`).
3. Every span must have a `latency_ms` field.
4. A span's `latency_ms`, when present, must not be negative.
5. `usage.prompt_tokens` and `usage.completion_tokens` must not be negative.
6. `tool_calls` must be a list of objects, each with a string `name`.

Validation runs at write time, in two places:

- `RunStore.append_trace(trace)` validates every trace and raises `ValueError` on problems, and also rejects a second trace for a case id already in the run, so an invalid or duplicate trace never reaches `traces.jsonl`.
- `TraceRecorder.finish(...)` validates before returning the trace, so systems that build traces manually fail loudly at the boundary instead of corrupting stored runs.

Reads do not re-validate: anything found in a stored run was validated on the way in. `Trace.from_dict` ignores fields it does not know, so traces written by a newer version with additional fields stay readable. `EvaluationEngine.evaluate_run` rejects duplicate traces for one case and traces for case ids that are not in the dataset.

## Run directory layout

Every experiment run writes one self-describing directory under `runs/`:

```
runs/<run_id>/
    manifest.json      run metadata
    traces.jsonl       one trace per line, one line per evaluation case
    eval_results.json  per-case results, aggregates, and engine config
```

When a comparison is requested, `write_regression_report` writes the regression JSON to the requested path (the demo writes it to `results/<stem>.json`).

Crash safety: each trace is appended to `traces.jsonl` and fsynced as soon as its case finishes, so an interrupted run keeps every case it completed. `manifest.json`, `eval_results.json` and regression reports are written to a temporary file in the same directory and moved into place with `os.replace`, so a reader never sees a half-written file and a failed write leaves the previous file intact. All files use LF line endings on every platform.

### manifest.json

Written by `RunStore.write_manifest`, from the `RunManifest` dataclass:

| Field | Description |
| --- | --- |
| `run_id` | Same id as the directory name |
| `name` | Human-readable run name (the demo uses the version name, e.g. `v1_baseline`) |
| `created_at` | Unix seconds |
| `system_config` | SUT config fingerprint, copied into every trace |
| `deterministic` | `SystemUnderTest.deterministic`: false for systems that sample, such as the real-LLM responder |
| `dataset_path` | Path of the evaluation dataset relative to the run's path root (POSIX separators), or just its file name when it lies outside that root, so no machine-specific absolute path is stored |
| `dataset_sha256` | SHA-256 of the dataset file, so the exact inputs are pinned; the regression engine refuses to compare runs whose hashes differ |
| `corpus_sha256` | SHA-256 of the document corpus (sorted doc id and text pairs) when the runner was given one, else null |
| `n_cases` | Number of cases in the dataset |
| `schema_version` | Currently `"1.1"` |

### traces.jsonl

One JSON object per line, in dataset order, appended by `RunStore.append_trace`. Read back with `load_run_traces(run_dir)`, which reconstructs `Trace` objects (including `Span` and `Usage`) via `Trace.from_dict`.

### eval_results.json

Written by `write_eval_results` after `EvaluationEngine.evaluate_run`:

```jsonc
{
  "per_case": [ /* one row per case: metrics, errors, latency_ms, total_tokens, token_source, cost_usd, failure */ ],
  "aggregates": {
    "mean_keyword_recall": 0.5503,       // mean over the cases where the metric applies
    "n_keyword_recall": 130,             // how many cases that mean averages
    "ci95_keyword_recall": [0.472, 0.6244], // seeded 95% bootstrap interval
    "mean_groundedness": 1.0,
    "n_groundedness": 130,
    "mean_retrieval_recall_at_3": 0.7154,
    "n_retrieval_recall_at_3": 130,
    "mean_latency_ms": 0.4631,           // successful cases only, like p50 and p95
    "p50_latency_ms": 0.45,
    "p95_latency_ms": 0.5855,
    "token_sources": ["heuristic"],      // sources mixed into mean_total_tokens
    "failure_counts": {"incomplete_answer": 21, "missed_abstention": 20, "retrieval_miss": 45},
    "n_cases": 150,
    "n_success": 64,
    "success_rate": 0.4267
    /* ... and the remaining mean_<metric>, n_<metric> and ci95_<metric> entries */
  },
  "missing_traces": [],                  // cases with no trace, scored as invocation_error
  "engine_config": {                     // settings in force, so results are self-describing
    "groundedness_threshold": 0.5,
    "keyword_threshold": 0.5,
    "price_per_1k": 0.0,
    "groundedness_min_overlap": 0.5,
    "recall_ks": [1, 3],
    "mrr_k": 3
  }
}
```

(Values from the committed `results/v1_baseline/eval_results.json`.) A metric key appears in a per-case row only when the case declares the corresponding expectation, and appears in aggregates only when at least one case produced it. `None` values (for example `groundedness` on an abstained answer) are excluded from means rather than treated as zero, which is why every mean sits next to its `n_<metric>`. A failed invocation is not `None`: it scores 0 on every answer-quality metric the case declares.

## Design rationale

- **Stored traces are never rewritten.** `RunStore` writes the manifest once and appends validated traces. A run is a measurement record, not a mutable cache; if the system or dataset changes, that is a new run with a new id, compared against the old one by the regression engine. Only `eval_results.json` is rewritten when a run is re-scored with newer metric code.
- **Evaluation reads traces, never re-runs the system.** `EvaluationEngine.evaluate_run` takes the trace list loaded from disk plus the dataset. Consequences: applying new metrics to old runs costs nothing, scoring is debuggable because every input and output is on disk, and evaluation cannot perturb the behavior it measures.
- **Replayability.** Because the manifest pins the dataset hash, the corpus hash and the system config, and traces pin the exact outputs, any two runs of the same deterministic version over the same dataset produce identical metrics (up to measured latency). This is what makes the committed results in `results/` and `reports/` verifiable by anyone with the repository, and it is why the demo system under test is deterministic.
- **Fail loudly at the write boundary.** Validation on write (rather than on read) means a schema violation stops the experiment immediately with a precise message (`invalid trace for case <id>: [...]`) instead of surfacing later as a silently skewed metric.
- **Provenance is part of the schema.** `token_source` on `Usage` and `attempt` and `wait_ms` on spans exist so that every number downstream can be traced back to how it was measured. Heuristic estimates are labelled as such instead of masquerading as API counts.
