# AIRE Trace Schema

This document specifies the JSON representation of a trace, the validation rules enforced at write time, and the layout of a stored run. The authoritative definitions are in `src/aire/schema.py` (dataclasses and `validate_trace_dict`) and `src/aire/tracing/storage.py` (`RunStore`).

## Overview

A trace is the complete, serialisable record of one system invocation for one evaluation case. Everything downstream (metrics, judges, failure classification, regression, reports) reads traces; nothing re-runs the system. All fields are JSON-serialisable, every trace is validated before it is stored, and stored runs are immutable.

## Field reference

### Trace (top level)

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `run_id` | string | yes | Id of the run this invocation belongs to (format `run_<8 hex>`) |
| `case_id` | string | yes | Id of the evaluation case, joins the trace to its `EvalCase` |
| `trace_id` | string | yes | Unique trace id (format `tr_<8 hex>`) |
| `system_config` | object | no | Fingerprint of the system version and config (for the demo: `top_k`, `min_score`, `style`, `weighting`, `allow_irrelevant`) |
| `started_at` | float | no | Invocation start, unix seconds |
| `final_answer` | string or null | no | The answer the system returned; null or empty means no answer was produced |
| `retrieved_doc_ids` | list of string | no | Document ids returned by retrieval, in rank order |
| `tool_calls` | list of object | no | Recorded tool calls; each carries `name`, `args`, and a `valid` flag from schema validation |
| `spans` | list of Span | no | Ordered, timed steps of the invocation |
| `usage` | Usage | no | Token accounting (defaults to zeros with `token_source: "unknown"`) |
| `error` | string or null | no | Non-null means the whole invocation failed (exception or timeout) |
| `trace_id` generation | | | Generated by `new_id("tr")` when not supplied |

### Span

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `kind` | string | yes | One of `retrieval`, `generation`, `tool_call`, `custom` |
| `name` | string | no | Human-readable step name, for example `v1_baseline.invoke` or `qdrant.search` |
| `started_at` | float | no | Span start, unix seconds |
| `latency_ms` | float | yes | Wall-clock duration in milliseconds; must not be negative |
| `attributes` | object | no | Free-form annotations (the runner writes `{"attempt": n}`) |
| `error` | string or null | no | Non-null means this span failed; set automatically by `TraceRecorder` span timers |

### Usage

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `prompt_tokens` | int | no | Prompt token count, must not be negative |
| `completion_tokens` | int | no | Completion token count, must not be negative |
| `token_source` | string | no | Provenance label: `api` (reported by a real backend), `heuristic` (estimated at about 4 characters per token by `estimate_tokens`), or `none`/`unknown`. Heuristic counters are allowed but must be labelled. |

`total_tokens` is a derived property (`prompt_tokens + completion_tokens`) and is not stored.

## Annotated example

A real trace from the committed v1 baseline run (`runs/run_4b4f7183/traces.jsonl`, case `refunds_request_window`), annotated:

```jsonc
{
  "run_id": "run_4b4f7183",              // joins all traces of one experiment
  "case_id": "refunds_request_window",   // joins to the EvalCase in the dataset
  "system_config": {                     // SUT fingerprint, identical for the
    "top_k": 1,                          // whole run; the regression engine and
    "min_score": 0.05,                   // reports use it to label versions
    "style": "faithful",
    "weighting": "overlap",
    "allow_irrelevant": false
  },
  "started_at": 1789573263.5698297,      // unix seconds
  "final_answer": "Northwind Cloud grants a refund window of 30 days ... [doc:doc_refunds]",
  "retrieved_doc_ids": ["doc_refunds"],  // rank order; read by recall@k and MRR
  "tool_calls": [],                      // empty: this system makes no tool calls
  "spans": [
    {
      "kind": "generation",              // timed step; a multi-step SUT would add
      "name": "v1_baseline.invoke",      // retrieval and tool_call spans here
      "started_at": 1789573263.5698297,
      "latency_ms": 0.6666,              // measured with Timer (perf_counter)
      "attributes": {"attempt": 1},      // retry bookkeeping by the runner
      "error": null
    }
  ],
  "usage": {
    "prompt_tokens": 13,                 // heuristic estimate (~4 chars/token)
    "completion_tokens": 58,
    "token_source": "heuristic"          // provenance label, not a real API count
  },
  "error": null,                         // non-null would classify as invocation_error
  "trace_id": "tr_7ab9fed1"
}
```

The corresponding `eval_results.json` row shows how the trace is scored against its case (`expected_keywords: ["30 days", "full refund", "payment card"]`, `supporting_doc_ids: ["doc_refunds"]`): `keyword_recall: 0.3333`, `citation_coverage: 1.0`, `groundedness: 0.5`, `retrieval_recall: 1.0`, `failure: "incomplete_answer"`.

## Validation rules

`validate_trace_dict(d)` returns a list of problems; an empty list means valid. Rules:

1. `run_id`, `case_id`, and `trace_id` must be present and non-empty.
2. Every span must have a `kind` field (reported as `span[i]: missing 'kind'`).
3. Every span must have a `latency_ms` field.
4. A span's `latency_ms`, when present, must not be negative.
5. `usage.prompt_tokens` and `usage.completion_tokens` must not be negative.

Validation runs at write time, in two places:

- `RunStore.append_trace(trace)` validates every trace and raises `ValueError` on problems, so an invalid trace never reaches `traces.jsonl`.
- `TraceRecorder.finish(...)` validates before returning the trace, so systems that build traces manually fail loudly at the boundary instead of corrupting stored runs.

Reads do not re-validate: anything found in a stored run was validated on the way in.

## Run directory layout

Every experiment run writes one self-describing directory under `runs/`:

```
runs/<run_id>/
    manifest.json      run metadata
    traces.jsonl       one trace per line, one line per evaluation case
    eval_results.json  per-case results, aggregates, and engine config
```

When a comparison is requested, `write_regression_report` writes the regression JSON to the requested path (the demo writes it to `results/<stem>.json`).

### manifest.json

Written by `RunStore.write_manifest`, from the `RunManifest` dataclass:

| Field | Description |
| --- | --- |
| `run_id` | Same id as the directory name |
| `name` | Human-readable run name (the demo uses the version name, e.g. `v1_baseline`) |
| `created_at` | Unix seconds |
| `system_config` | SUT config fingerprint, copied into every trace |
| `dataset_path` | Path of the evaluation dataset used |
| `dataset_sha256` | SHA-256 of the dataset file, so the exact inputs are pinned |
| `n_cases` | Number of cases in the dataset |
| `schema_version` | Currently `"1.0"` |

### traces.jsonl

One JSON object per line, in dataset order, produced by `flush_traces`. Read back with `load_run_traces(run_dir)`, which reconstructs `Trace` objects (including `Span` and `Usage`) via `Trace.from_dict`.

### eval_results.json

Written by `write_eval_results` after `EvaluationEngine.evaluate_run`:

```jsonc
{
  "per_case": [ /* one row per case: metrics, latency_ms, total_tokens, cost_usd, failure */ ],
  "aggregates": {
    "mean_keyword_recall": 0.5758,       // mean over cases where the metric applies
    "mean_citation_coverage": 0.7273,
    "mean_retrieval_recall": 0.7273,
    "mean_abstention_correct": 0.0,
    "failure_counts": {"incomplete_answer": 9, "retrieval_miss": 1, "missed_abstention": 4},
    "n_cases": 26,
    "n_success": 12
  },
  "missing_traces": [],                  // cases with no trace, classified invocation_error
  "engine_config": {                     // thresholds in force, so results are self-describing
    "groundedness_threshold": 0.5,
    "keyword_threshold": 0.5,
    "price_per_1k": 0.0
  }
}
```

A metric key appears in a per-case row only when the case declares the corresponding expectation, and appears in aggregates only when at least one case produced it. `None` values (for example `groundedness` on an abstained answer) are excluded from means rather than treated as zero.

## Design rationale

- **Stored runs are immutable.** `RunStore` writes the manifest once, appends validated traces, and flushes once. Nothing rewrites a run directory after the fact. A run is a measurement record, not a mutable cache; if the system or dataset changes, that is a new run with a new id, compared against the old one by the regression engine.
- **Evaluation reads traces, never re-runs the system.** `EvaluationEngine.evaluate_run` takes the trace list loaded from disk plus the dataset. Consequences: applying new metrics to old runs costs nothing, scoring is debuggable because every input and output is on disk, and evaluation cannot perturb the behavior it measures.
- **Replayability.** Because the manifest pins the dataset hash and the system config, and traces pin the exact outputs, any two runs of the same version over the same dataset produce identical metrics (up to measured latency). This is what makes the committed results in `results/` and `reports/` verifiable by anyone with the repository, and it is why the demo system under test is deterministic.
- **Fail loudly at the write boundary.** Validation on write (rather than on read) means a schema violation stops the experiment immediately with a precise message (`invalid trace for case <id>: [...]`) instead of surfacing later as a silently skewed metric.
- **Provenance is part of the schema.** `token_source` on `Usage` and `attributes.attempt` on spans exist so that every number downstream can be traced back to how it was measured. Heuristic estimates are labelled as such instead of masquerading as API counts.
